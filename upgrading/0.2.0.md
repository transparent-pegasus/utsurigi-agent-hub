# Upgrading to 0.2.0

Applies when upgrading from 0.1.x.

`storage.provider` now defaults to `google-drive`. Configs that omitted it used
R2; set `provider: r2` explicitly to keep R2.
Until the YAML is fixed, every command fails, including scheduled `sync --scheduled`
and `live check`, and scheduled retries stop. A hub written from more than one
machine keeps `r2`. An existing hub cannot move between `r2` and
`google-drive`/`local` in place: the CLI rejects registry entries whose URLs do not
match `storage.provider`.

`shared-revision.json` (version 3) and `decisions.yaml` (version 2) now identify the
shared repository by its restic repository ID instead of the SHA-256 of its URL, so
they stay valid when the repository moves to another path. 0.1.x binaries reject
these versions.

1. Upgrade every Bot and machine in the hub before any of them runs `setup` or
   `registry publish` with 0.2.0.
2. Nothing else is required. The next shared publication writes `shared-revision.json`
   version 3. A `decisions.yaml` version 1 stays valid; [INIT.md](../INIT.md)
   describes version 2.
3. To move `google-drive` or `local` repositories to new paths, for example after a
   Drive generation was restored on another host:
   - Copy each repository exactly, so that the copy is the same restic repository.
     The old paths may then be deleted. Do not put a fresh `restic init` in place of
     a deleted repository: publication refuses it for a shared Bot repository whose
     old password this host holds.
   - Point the config's repository URLs at the copies.
   - Copy the authoring base from the verified `status.active_shared`. Keep its
     version 1 `decisions.yaml` unchanged or rewrite its `repository_sha256` for the
     new URL; use version 2 only once `active_shared` has a `repository_id`.
   - Set this Bot's registry entry to its new repository path. Then run
     `registry publish`, with `--takeover` if the runtime changed.

   Until that publication, `sync` on this host fails because the registry still names
   the old path; after it, `sync` works again (a new runtime runs `setup` first).
   Publication accepts a registered shared Bot repository whose old password this
   host holds and that is missing at its old path only when the new registry names
   the same Bot at a repository whose restic ID `registry-history.json` already
   records, such as an exact copy.
